# Deploy JyotiCVE on Render

The repository includes a Render Blueprint (`render.yaml`) for the dashboard and all three bots in one Python web service. Gunicorn serves the authenticated dashboard; a supervised subprocess runs the scheduler. SQLite history, inventory, configuration, and schedule preferences live on a persistent disk.

## Deploy from your repository

1. Commit and push these deployment files to the GitHub branch you want Render to deploy. The selected branch must contain **`render.yaml`** and **`jyoticve/hosted.py`**. Local changes are not available to Render until pushed.
2. In Render, select **New → Blueprint**, connect your repository, and select that branch.
3. Review the service and persistent disk, then create the Blueprint. **This uses a paid web service and a persistent disk**, not Render's free service.
4. After deployment, open the service's **Environment** settings and reveal the generated **`JYOTICVE_ADMIN_PASSWORD`**. Keep this value private.
5. Open the service's HTTPS URL. The browser displays a sign-in prompt. Use username **`admin`** and the generated password.
6. In **Monitored assets**, add your domains and actual deployed technologies. The initial inventory is empty; the deployment does not infer your assets from sample files.
7. In **Settings**, configure notification channels. Console delivery works immediately and appears in Render logs; a real team destination requires its environment variable and channel configuration.

Monitoring starts automatically on the first deployment. General security intelligence runs immediately; certificates and stack coverage require configured assets. The dashboard's **Pause monitoring** preference persists across redeploys. Click **Start monitoring** to resume. Previews do not send notifications or persist findings.

## Service settings

The Blueprint supplies these values. Use the same settings if creating a Web Service manually:

| Setting | Value |
| --- | --- |
| Runtime | Python |
| Python version | Latest patch of Python 3.13, selected by `.python-version` |
| Build command | `pip install '.[hosted]'` |
| Start command | `gunicorn --config deploy/gunicorn.conf.py 'jyoticve.hosted:create_app()'` |
| Health check | `/healthz` |
| Persistent disk mount | `/var/data` |
| Initial disk size | 1 GB |
| Instance count | 1 |
| Data directory | `/var/data/jyoticve` |

The Gunicorn configuration binds to `0.0.0.0:$PORT`, uses exactly one worker with eight request threads, and shuts down child processes on service termination. Do not enable multiple workers, multiple instances, or autoscaling with this local SQLite/file-lock design.

Render automatically sets `RENDER_EXTERNAL_URL`, which is used to validate the public Host and Origin. All dashboard pages and APIs require HTTP Basic authentication over Render's HTTPS endpoint. The unauthenticated health check only reports `ok` or `unavailable`. Writes additionally require the dashboard's CSRF token and the configured HTTPS Origin. Passwords are not stored in configuration, database records, or frontend code.

For a custom domain, set **`JYOTICVE_PUBLIC_ORIGIN=https://security.example.com`** and redeploy. Use that exact origin to open the dashboard; other hosts are rejected. Render terminates HTTPS before forwarding requests to Gunicorn. Keep this hosted entrypoint behind an HTTPS reverse proxy if deploying somewhere else.

## Environment variables

| Variable | Required? | Purpose |
| --- | --- | --- |
| `JYOTICVE_ADMIN_USER` | Blueprint sets `admin` | Dashboard username |
| `JYOTICVE_ADMIN_PASSWORD` | Yes; generated by Blueprint | Dashboard password, at least 24 characters |
| `JYOTICVE_DATA_DIR` | Yes; Blueprint sets it | Absolute directory on the persistent disk |
| `RENDER_EXTERNAL_URL` | Render provides it | Public HTTPS origin |
| `JYOTICVE_PUBLIC_ORIGIN` | Optional | Override for your custom HTTPS domain |
| `NVD_API_KEY` | Optional | Higher NVD request allowance |
| `SECURITY_SLACK_WEBHOOK` | If Slack is selected | Your incoming webhook URL |
| `SECURITY_TEAMS_WEBHOOK` | If Teams is selected | Adaptive Card workflow receiver URL |
| `SECURITY_WEBHOOK` | If a generic webhook is selected | Your HTTPS event receiver URL |

Set secrets in **Render → Service → Environment**, then save and redeploy. Do not commit `.env` or paste secret URLs into the dashboard's environment-variable-name field. The application reads provider environment variables directly; `.env` is not automatically loaded.

For Slack, add a channel in dashboard Settings with a stable ID, type `slack`, and destination variable **`SECURITY_SLACK_WEBHOOK`**. The variable must already exist in the running service before saving the channel. The same pattern applies to Teams and generic webhooks. Existing channel IDs identify pending deliveries: removing/renaming an ID can leave its queued deliveries awaiting configuration.

This is a single-administrator dashboard, not a multi-user identity system. Browsers cache HTTP Basic credentials; use a private browsing window on shared computers. Rotate the password in Render and redeploy when necessary.

## Persistence, restarts, and logs

On first startup the application creates these files if absent:

```text
/var/data/jyoticve/
  config.json
  domains.txt
  inventory.json
  state/monitor.sqlite3
```

Existing files are preserved during redeploys. Dashboard edits are written to the persistent disk, not committed back to GitHub. Changing `config.example.json` in the repository does not overwrite a deployed workspace; use the dashboard to change existing settings. The packaged bootstrap defaults live in `jyoticve/default-config.json`.

The supervisor restarts a scheduler that exits unexpectedly without requiring an open browser. Scheduler and notification logs go to Render's log stream, using UTC execution timestamps. Manual scan output is available in Run history for the current dashboard session. Live execution records, cursors, alerts, and delivery progress persist in SQLite; preview output does not survive process restarts.

Graceful shutdown gives child processes up to 20 seconds to finish before terminating them. Source cursors and queued delivery state support retry after restart. A crash after a notification was accepted can still cause a duplicate delivery: delivery remains at least once. Source/API failures are reported in execution history; they do not force service restarts through the health check.

Keep disk backups using SQLite's backup API (or stop scans before a file-level backup). Watch disk usage because history is retained indefinitely. Render services with attached disks can have downtime during redeploys. Long NVD backfills can take time; the dashboard stays responsive while those scans run.

## Verify a deployment

- `/healthz` returns `{"status":"ok"}` without credentials.
- Opening `/` prompts for login; `/api/state` is not accessible anonymously.
- Add a domain and run **Preview scan**; inspect its output without sending notifications.
- Change an asset or setting, redeploy, and confirm it remains.
- Check Overview and Run history for scheduler activity and collection errors.

Local development is unchanged: `python -m jyoticve web` remains a loopback-only dashboard without a login prompt. Use the hosted factory and required environment variables only for public deployment.

## Why the earlier Vercel build failed

The Vercel suggestion `entrypoint = "jyoticve.web:Handler"` only identifies a class; it does not initialize the custom local server or provide the durable scheduler and storage the app needs. The Render integration does not make the app serverless. Keep the full service on Render; a future Vercel deployment would need external storage and a redesigned job execution model.
